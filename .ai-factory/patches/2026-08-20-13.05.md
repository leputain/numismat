# Telegram WebView supplied a non-canonical Origin during signed login

**Date:** 2026-08-20 13:05
**Files:** `src/finbot/adapters/http/routes/auth.py`, `tests/unit/test_http_auth.py`, `AGENTS.md`, `SECURITY.md`
**Severity:** high

## Problem

The first compatibility fix allowed a missing `Origin`, but native Telegram still showed a configuration error. Production telemetry proved that the signed login request carried one present Origin value that did not equal the public Mini App URL, so the request was still rejected before Telegram proof verification.

## Root Cause

The initial mitigation assumed native WebViews either send the canonical public Origin or omit it. In practice Telegram clients do not expose one portable browser Origin contract. Treating this transport metadata as an authentication authority was therefore incompatible with a legitimate signed client.

## Solution

`POST /api/v1/auth/telegram` now accepts either no Origin or one non-empty bounded ASCII Origin. It still rejects duplicate, empty, oversized, or non-ASCII values. Login authority remains the bounded Telegram `initData`, official HMAC, exact configured owner, short TTL/skew, and replay denial.

Logout and every protected mutation continue to require the exact configured Origin plus the existing session and CSRF checks. No raw Origin or authentication material is logged.

## Prevention

- Model WebView headers as transport metadata unless the platform provides a stable documented contract.
- Keep regression cases for both omitted and non-canonical single Origin values on signed login.
- Keep explicit regression coverage that duplicate login Origin and missing logout Origin fail closed.
- Do not reuse initial proof-exchange assumptions for cookie-authenticated state-changing requests.
