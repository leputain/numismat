# Native Telegram login rejected when WebView omitted Origin

**Date:** 2026-08-20 12:41
**Files:** `src/finbot/adapters/http/routes/auth.py`, `tests/unit/test_http_auth.py`, `AGENTS.md`, `SECURITY.md`
**Severity:** high

## Problem

The owner-only Mini App repeatedly showed `origin_forbidden` during initial authentication on a native Telegram client even though the canonical HTTPS host, menu button, proxy chain, certificates, and API were healthy.

## Root Cause

The initial signed Telegram login treated `Origin` as unconditionally required. Native Telegram WebViews may omit that header, while the authentication boundary already has stronger authoritative gates: bounded `initData`, official Telegram HMAC verification, exact configured owner, a short `auth_date` window, and one-time proof replay denial.

The unconditional header requirement therefore rejected a legitimate native launch before the signed Telegram proof could be checked.

## Solution

The initial `POST /api/v1/auth/telegram` now permits an absent `Origin`. When the header is present it must still match the canonical Mini App origin exactly, and duplicates remain rejected. Logout and every protected mutation retain mandatory exact-Origin and double-submit CSRF checks.

The existing privacy-safe auth completion event remains the runtime verification signal; no Origin, header, cookie, token, or `initData` value is logged.

## Prevention

- Distinguish initial signed Telegram proof exchange from cookie-authenticated state-changing requests.
- Preserve exact-Origin checks whenever a client supplies the header and on every protected mutation.
- Keep a regression test for a valid signed native login without `Origin`, alongside wrong/duplicate-Origin rejection tests.
- Do not weaken HMAC, owner, TTL, replay, cookie, or CSRF boundaries to address WebView compatibility.
